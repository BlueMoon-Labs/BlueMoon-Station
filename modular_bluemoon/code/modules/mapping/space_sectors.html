Секторы космоса
modular_bluemoon/code/modules/mapping/space_sectors/README.md

Инструмент для карт, которым нужен предсказуемый космос: нарисованные .dmm вместо случайных пустышек с руинами, и фиксированные переходы между ними вместо случайной раскладки, которая перетасовывается каждый раунд.

Без объявленного набора всё работает как раньше: space_ruin_levels пустышек, случайные руины, случайные соседи.

Как объявить набор

Секторы объявляются подтипами /datum/space_sector в коде — так путь к карте, id и ссылки на соседей проверяет компилятор и юнит-тест, а не рантайм на живом раунде.

/datum/space_sector/icebox
	abstract_type = /datum/space_sector/icebox
	sector_set = "icebox"

/datum/space_sector/icebox/hub
	id = "icebox_hub"
	name = "Перевалочный узел"
	mappath = "_maps/map_files/bluemoon_sectors/icebox_hub.dmm"
	sector_x = 0
	sector_y = 0

/datum/space_sector/icebox/north
	id = "icebox_north"
	name = "Северный дрейф"
	mappath = "_maps/map_files/bluemoon_sectors/icebox_north.dmm"
	sector_x = 0
	sector_y = 1

Файл кладётся в modular_bluemoon/code/modules/mapping/space_sectors/ и включается в tgstation.dme.

Карта заказывает набор одной строкой в своём json:

"space_sectors": "icebox",
"space_ruin_levels": 0

space_ruin_levels: 0 означает «кроме объявленных секторов ничего не создавать». Ненулевое значение оставит и случайные пустышки — они сядут в свободные клетки вокруг объявленных.

Поля декларации

ПолеЧто делает
idУникальный идентификатор. По нему на сектор ссылаются links соседей.
sector_setИмя набора. Карта включает набор целиком.
nameИмя z-уровня: видно админам, в дампах и в логах.
mappathПуть к .dmm от корня репозитория, начиная с _maps/. null — пустой уровень без карты.
sector_x, sector_yКлетка сетки. X растёт на восток, Y на север, начало координат произвольное.
sector_layerЭтаж вертикальной стопки.
traitsТрейты поверх ZTRAITS_SPACE: гравитация, базовый турф, профиль параллакса, погода, прозрачный космос.
ruin_budget0 — случайных руин не будет. Число — засеять этот уровень отдельным проходом с таким бюджетом. -1 — отдать уровень общему проходу вместе с обычным космосом.
link_north, link_south, link_east, link_westЯвная связь по краю поверх координат: id сектора, в который ведёт эта сторона.

Края и соседи

Соседство считается по клеткам: улетел за восточный край — попал в сектор, объявленный восточнее. Край, за которым клетки нет, заворачивает на дальний конец ряда, то есть космос замкнут сам на себя и никуда не обрывается.

link_north/link_south/link_east/link_west перебивают координаты на своих сторонах; всё остальное соседство остаётся посчитанным по клеткам. Взаимность не подразумевается: если сосед должен смотреть назад, у него должна быть своя строчка. Односторонний край — законная топология, но валидация о нём скажет, потому что чаще это забытая строчка.

/datum/space_sector/icebox/east
	id = "icebox_east"
	sector_x = 1
	// по координатам западный сосед - узел, но связь уводит на север
	link_west = "icebox_north"

Вертикаль

Секторы с одинаковыми sector_x/sector_y и соседними sector_layer сцепляются взаимными ZTRAIT_UP/ZTRAIT_DOWN. Между такими этажами работают все штатные способы вертикального движения, включая вербы Move Upwards и Move Down: в невесомости для них не нужен ни джетпак, ни лестница.

Если в одном .dmm нарисовано несколько z, сектор занимает столько этажей подряд, начиная со своего, и стопка собирается сама.

Этаж стопки без соседа на своей высоте выводит за край к соседней клетке, на её ближайший этаж ниже. Обратный край соседа ведёт на нижний этаж стопки, но улетевший возвращается на тот этаж, с которого улетел: номер этажа помнит сам атом (space_departure_floor).

Два замечания по картинке и по воздуху:

  • чтобы видеть нижний этаж, уровень должен попросить прозрачный космос — см. раздел ниже. Без этого космос вертикаль пропускает, но сквозь него ничего не видно;
  • воздух между этажами через космос не течёт: zAirIn/zAirOut не трогали намеренно. Вертикальная атмосфера — это отдельная механика, и включать её заодно с проходимостью было бы сюрпризом.

Видимая многослойность

Обычный космический турф рисует звёздную подложку параллакса и потому непрозрачен: стоя над станцией, игрок видит звёзды, а не палубу под ногами. Трейт ZTRAIT_TRANSPARENT_SPACE снимает подложку со всего космоса уровня и показывает вместо неё этаж снизу — как нарисованный маппером /turf/open/space/transparent, только на весь уровень разом.

/datum/space_sector/icebox/orbit
	id = "icebox_orbit"
	sector_x = 0
	sector_y = 0
	sector_layer = 1
	// с этого этажа видно тот, что лежит под ним
	traits = list(ZTRAIT_TRANSPARENT_SPACE = TRUE)

Что важно знать:

  • трейт ставится верхнему этажу, тому, с которого смотрят. Нижнему он не нужен, если под ним самим ничего нет;
  • этаж снизу приезжает готовой картинкой: со своим светом, своим параллаксом, чуть притушенный и сжатый на MULTIZ_SCALE_PER_LEVEL за уровень — так читается глубина;
  • пока этажа снизу нет (не загрузился или его вообще не объявили), турф остаётся обычным космосом со звёздами, а не чёрной дырой;
  • это стоит рендера: каждый такой турф держит в vis_contents турф снизу, а нижний этаж собирается отдельным комплектом plane master'ов. Поэтому трейт заказывают, а не получают по умолчанию. Игрок может ограничить глубину настройкой «Многоуровневый рендер» в настройках графики — тогда он увидит обычный звёздный космос, а не черноту: звёзды остаются подложкой под картинкой нижнего этажа;
  • связка обязана строить плоскостной куб. ZTRAIT_NO_PLANE_STACK на той же стопке куб отключает — прозрачность после этого покажет нижний этаж без его собственного света; про такое сочетание загрузка пишет претензию в лог маппинга.

Ровно тот же трейт работает и в json обычной карты, без секторов:

"traits": [{"Linkage": "Cross"}, {"Station": true, "Transparent Space": true}]

Посмотреть глазами, ничего не рисуя:

powershell -ExecutionPolicy Bypass -File tools/multiz_test/run_multiz.ps1

Стенд multiz_debug — три уровня, у верхних двух трейт уже включён. Колонка «прозрачный космос» в дампе связок (Debug → Multi-Z: панель) показывает, кто его заказал и досталось ли заказчику что показывать.

Гейты

Переход не по краю карты, а из точки в точку: два /obj/effect/sector_gate с одинаковым gate_id. Всё, что заходит на один, выходит за вторым по направлению движения; если там стена или край карты — встаёт на сам гейт. Направление и дрейф переход переживают.

Гейты могут стоять на разных картах и грузиться в любом порядке — пара ищется по id после загрузки всего. Непарный gate_id ничего не ломает: гейт просто молчит, а претензия уходит в лог маппинга и в отладочную панель.

Буксируемых и пристёгнутых гейт за собой не тащит — через него проходит ровно то, что на него зашло.

Отладка

  • Debug → Секторы космоса: сетка — картинка сетки по этажам, куда ведёт каждый край, какие стопки собрались, состояние гейтов и полный список претензий валидации. Дамп падает файлом в data/multiz_debug/.
  • Тот же отчёт уходит в лог маппинга при загрузке набора, так что перекос топологии видно по логу раунда, не заходя в игру.
  • Debug → Multi-Z: панель — соседняя панель про вертикаль: связки, плоскости, почему сквозь дыру ничего не видно.

Юнит-тесты набора лежат в code/modules/unit_tests/space_sectors.dm. Тест space_sector_declarations прогоняет валидацию по всем объявленным в коде секторам, поэтому опечатка в пути к карте или задвоенный id валят CI, а не раунд.
