# NETRUN: внешнее C#-ядро сетевой симуляции

Статус: проект для реализации и проверки; код не реализован.
Дата: 2026-11-01.
Основание: обсуждение переноса основы NETRUN из основного потока BYOND.

## 1. Задача и ожидаемый результат

Основные проблемные области сервера: построение сетевой архитектуры, маршрутизация и запросы между машинами. Необходимо вынести их вычислительную и транспортную основу в самостоятельное C#-ядро. BYOND сохраняет владение игровым миром и выполнение конечных действий машин.

Целевое поведение: BYOND передаёт изменения мира и новые обращения ограниченными пакетами; C# самостоятельно строит граф, рассчитывает маршруты, моделирует движение сообщений и возвращает готовые обращения к сервисам. BYOND не участвует в каждом переходе пакета.

Это не перенос DM-procs в произвольные потоки и не универсальная библиотека параллельного выполнения DM. Это выделение предметной модели NETRUN с независимым исполнением. Производительность считается по полному циклу, включая сбор данных, сериализацию, обмен и применение результатов.

Документ фиксирует целевую архитектуру. Предложенные имена сообщений, проектов и методов не являются существующим API. Спорные игровые правила сначала извлекаются из кода и тестов; миграция не должна менять их по умолчанию.

## 2. Область работ

### Первая обязательная область

- Реестр сетевых узлов и объявленных сервисов.
- Сетевые сегменты, инфраструктура, привязка конечных устройств, связи и их стоимость.
- Пространственные индексы, построение и обновление топологии.
- Доступность, маршрутизация, кэши и инвалидирование.
- Межмашинный транспорт: очереди, переходы, задержки, приоритеты, таймауты и отказы.
- Корреляция запросов/ответов, отмена, объединение заменяемых состояний.
- Наблюдаемость, восстановление и ограничение нагрузки.

### Последующие расширения

Сетевые сессии, протоколы, сетевые политики, discovery, виртуальные агенты и другие механики могут переходить в ядро после стабилизации основы. Только сетевой граф без транспорта не считается завершением основной миграции.

### Вне первой миграции

- Переписывание TGUI, боя, физических машин и игровых сущностей.
- Новая балансировка стоимости маршрутов, задержек или прав доступа.
- Замена BYOND-сетевого соединения с игроками.
- Прямой доступ C# к памяти DM-объектов.
- Обязательное постоянное хранение симуляции между раундами.
- Доступ к ядру из браузера игрока.

## 3. Исходная система и точки интеграции

В `dependencies.sh` указаны BYOND 516.1688 и rust_g 6.2.0. Это исходная конфигурация для проверки, а не гарантия совместимости будущего моста. Рабочее дерево на момент подготовки документа было чистым.

Пути ниже указаны относительно `modular_bluemoon/code/modules/netrun/`:

| Модуль | Текущая роль / целевая работа |
|---|---|
| `core/subsystem.dm` | Очереди обновлений и публикаций, бюджет исполнения; будущий координатор обмена |
| `core/task_scheduler.dm`, `core/execution_limits.dm` | Планирование DM-задач; оставить только работу, которой нужен BYOND |
| `core/topology.dm` | Read-only проекция графа из C# и реакция на события; построение инфраструктуры и биндинги APC уже перенесены в ядро |
| `integration/external_projection.dm` | Импорт графа и биндингов из ядра; прежние `core/apc_prebuild.dm`, `core/apc_spatial_index.dm`, `core/apc_bridges.dm` удалены |
| `core/routes.dm`, `core/machine_routes.dm` | Read-only таблицы маршрутов из ядра и проверка живого состояния native-машин |
| `core/machine_transport.dm` | Сообщения, payload, coalescing и транспорт; отделить от исполнения DM-сервисов |
| `core/service_registry.dm`, `core/service_discovery.dm` | Объявления сервисов и адаптеры; физические обработчики оставить в DM |
| `core/requests.dm`, `core/delivery.dm`, `core/delivery_tasks.dm` | Жизненный цикл доставки и отмена; проверить всех потребителей перед заменой |
| `core/packet_context.dm`, `core/access_events.dm` | Контекст и события; согласовать с единым жизненным циклом запроса |
| `core/map_view.dm`, `core/console_ui.dm` | Использовать проекции, исключить скрытые синхронные перестроения графа |

Уже существуют очереди, приоритеты, бюджет прохода, ревизии маршрутов, LRU-кэш и событийное обновление инфраструктуры. Они уменьшают работу, но выполняются в основном потоке. Не заменять их более примитивным полным сканированием при переносе.

Особенно важно сохранить текущую геометрию: связанные Z-уровни, сектор и порядок этажей, метрику расстояния, правила выбора APC и детерминированное разрешение равенств. Координаты сами по себе недостаточны для воспроизведения этих правил.

Полный аудит call sites и контрактов ещё не проведён. Перечень выше — карта начала работ, а не исчерпывающий список изменяемых файлов.

## 4. Архитектурные решения

1. `Netrun.Core` — независимая библиотека C# без BYOND ABI, IPC и DM-ссылок.
2. `Netrun.Host` — отдельный локальный процесс, содержащий ядро, соединение и диагностику.
3. DM-адаптер — преобразует события игрового мира в факты и применяет обращения к сервисам.
4. Небольшой нативный мост — предоставляет BYOND ограниченные неблокирующие операции обмена. Существующий rust_g не расширять автоматически: сначала проверить доступные средства и стоимость отдельного моста.
5. Сетевое состояние изменяет один последовательный обработчик C#. Независимые расчёты можно вынести в рабочие потоки только после измерений и с версионированными неизменяемыми входами.
6. Логика работает по игровому времени BYOND; физическое время обслуживает heartbeat и эксплуатационные таймауты.
7. Обмен пакетный, очереди ограничены. Полный снимок — для инициализации и восстановления, изменения — для обычной работы.
8. Только один движок имеет право вызывать игровые эффекты в каждый момент времени.

```text
DM-мир → DM-адаптер → неблокирующий мост → локальный IPC
                                              ↓
                                  Netrun.Host / Netrun.Core
                                  модель → граф → транспорт
                                              ↓
DM-сервисы ← проверка и применение ← пакет выходных событий
```

Отдельный процесс выбран для изоляции сбоев и самостоятельного профилирования. Протокол не зависит от конкретного IPC. Предварительный вариант транспорта — loopback TCP с кадрами длина + UTF-8 JSON; named pipes/Unix sockets допустимы после проверки среды. Не использовать HTTP-запрос на каждый переход пакета.

Конкретные .NET SDK/TFM, RID, язык моста, ABI и способ запуска пока не утверждены. Выбрать их на этапе 0 по фактической серверной ОС, разрядности DreamDaemon и способу развёртывания. Ядро в отдельном процессе не требует Native AOT; AOT не является условием проекта.

## 5. Владение данными и модули ядра

| Владелец | Данные |
|---|---|
| BYOND | Существование физических объектов, координаты, питание, повреждения, реальные пользователи и права, исполнение операций |
| C# | Производный граф, сетевые индексы, маршруты, пакеты в пути, очереди, сетевые таймеры и сетевые сессии после их миграции |
| DM-проекция | Только кэш опубликованного сетевого представления для совместимости и UI |

`WorldMirror`: принятые факты об узлах, сервисах, секторах и конфигурации.

`Topology`: пространственные индексы, привязки, физические/логические связи, публикация целого графа.

`Routing`: поиск пути, достижимость, bounded-кэши, зависимости результатов от ревизий.

`Transport`: очереди, виртуальные переходы, сроки, приоритеты, delivery и завершение.

`Protocols`: контракты request/response, объявления возможностей и сетевые политики.

`Projection`: изменения сетевой карты и диагностика по подпискам; промежуточные переходы не обязаны публиковаться отдельными сообщениями.

`Runtime`: входные/выходные очереди, логическое время, режимы, ограничения, журнал и метрики.

Обработчики сервисов машин остаются в DM. Например, ядро доставляет типизированное обращение к устройству; открытие двери или изменение настроек выполняет её штатный адаптер с текущими проверками.

## 6. Идентификаторы и ревизии

| Поле | Смысл |
|---|---|
| `world_epoch` | Уникальная инкарнация запущенного DM-мира; меняется при новом запуске |
| `engine_epoch` | Инкарнация C#-процесса; меняется после его рестарта |
| `binding_epoch` | Поколение активного владения движком; меняется при переключении и полном resync |
| `node_id`, `generation` | Логический ID и поколение физического узла |
| `node_revision` | Версия экспортируемых фактов узла |
| `service_id`, `service_revision` | Тип/экземпляр сервиса и версия его объявления |
| `input_sequence`, `output_sequence` | Независимые последовательности кадров в двух направлениях |
| `applied_sequence` | Последний атомарно применённый входной кадр |
| `graph_version`, `graph_input_sequence` | Опубликованный граф и граница входов, на которой он построен |
| `request_id`, `invocation_id` | Идентичность запроса и конечного обращения к DM-сервису |

ID и счётчики обмена передаются строками: не полагаться на точное представление больших целых в DM/JSON. Малые координаты, флаги и интервалы могут быть числами в явно заданном диапазоне. DM-ссылки, пути типов и произвольные proc names не являются адресами протокола.

Сетевой адрес отделён от ID объекта: переиспользование адреса не доставляет старые пакеты новой машине. Пересоздание компонента и замена машины требуют явного правила изменения поколения.

## 7. Синхронизация мира

### Начальный снимок

Состояния соединения: `Disconnected → Handshaking → Snapshotting → CatchingUp → Ready`. Ошибка целостности переводит в `ResyncRequired`; потеря процесса — в `Unavailable`.

1. Handshake согласует major/minor протокола, возможности, epochs и лимиты.
2. DM начинает снимок с `snapshot_id` и границей журнала изменений.
3. Узлы, объявления сервисов, сектора/связность Z и конфигурация передаются ограниченными chunks.
4. Пока снимок собирается, изменения и удаления журналируются в DM. Сбор не блокирует весь игровой тик.
5. `SnapshotCommit` содержит число записей и контроль целостности. C# собирает снимок в staging-модель, не обслуживая по ней live-запросы.
6. Журнал после границы воспроизводится по порядку. Изменившийся во время чтения объект допускает повторную запись с большей ревизией; tombstones запрещают его воскрешение.
7. После catch-up и публикации согласованного графа ядро выдаёт `Ready` с границей входов. Только затем можно включить live-доставку.

Точный алгоритм разбиения обхода и журналирования проверить тестом удаления/пересоздания объекта посреди снимка. При переполнении журнала снимок отменяется и начинается заново с диагностикой, а не продолжается с потерянными изменениями.

### Обычные изменения

DM собирает события регистрации, удаления, перемещения, питания, сетевой конфигурации и сервисов. Объединяет заменяемые обновления до назначения последовательности кадру. Удаления и команды нельзя терять при объединении.

Пакет сначала полностью валидируется, затем атомарно применяется к mirror; частичное применение запрещено. Повтор кадра не применяется второй раз. Пропуск последовательности приостанавливает приём следующих кадров и вызывает replay из ограниченного журнала либо resync.

Принятие мостом в очередь, получение Host и применение ядром — разные события. Протокол использует cumulative ACK именно применения. Аналогично выходной ACK означает обработку DM, а не чтение байтов сокета.

Изменения питания, удаления и отзыва доступа немедленно обновляют ограничивающий слой доступности. Дорогой новый граф строится отдельно. До его публикации запросы, затрагивающие грязную область, получают ожидание либо отказ `topology_pending`; нельзя выдать маршрут через заведомо недействительную связь старого графа. Начальная реализация может консервативно задерживать все новые маршруты во время перестройки.

### Порядок и причинность

Входной кадр содержит упорядоченный массив `entries`. Не разделять изменения и команды на независимые массивы с неявным порядком. Команда зависит от всех предшествующих ей записей. В кадр включается объявленная граница логического времени.

Адаптер обязан экспортировать известные ему изменения до связанной команды. Физический мир может измениться после этой границы; конечные DM-проверки остаются обязательными. Полной транзакции между миром DM и внешней симуляцией нет.

## 8. Протокол v1: проект контракта

Кадр: unsigned 32-bit длина тела в network byte order, затем UTF-8 JSON. Лимит длины проверяется до выделения памяти; поток допускает частичное чтение и несколько кадров за чтение. Максимумы и negotiated limits фиксируются в спецификации до реализации.

Пример входа (имена и значения иллюстративные):

```json
{
  "protocol_major": 1,
  "protocol_minor": 0,
  "world_epoch": "world-a",
  "engine_epoch": "engine-b",
  "binding_epoch": "binding-c",
  "sequence": "1842",
  "ack_output_sequence": "1700",
  "simulation_time_ds": 9250,
  "entries": [
    {
      "kind": "node_upsert",
      "node_id": "n317",
      "generation": "2",
      "node_revision": "41",
      "state": {
        "address": "example-address",
        "node_type": "server",
        "position": {"x": 10, "y": 20, "z": 2},
        "sector_id": "s1",
        "online": false
      }
    },
    {
      "kind": "request_submit",
      "request_id": "r9081",
      "source": {"node_id": "n102", "generation": "1"},
      "destination": {"node_id": "n450", "generation": "3"},
      "service": "example.status",
      "operation": "read",
      "deadline_ds": 9280,
      "payload": {}
    }
  ]
}
```

`node_upsert.state` — полное экспортируемое состояние узла для данной ревизии, не произвольный partial patch. Поля сетевых возможностей и политики добавляются после аудита фактической модели. Параметры сектора и связности Z передаются отдельными версионированными записями.

### Семейства сообщений

| Направление | Сообщения |
|---|---|
| Оба | `hello`, `hello_ack`, `heartbeat`, `ack`, `resync_required`, `shutdown` |
| DM → Host | `snapshot_begin`, `snapshot_chunk`, `snapshot_commit`, `node_upsert`, `node_remove`, `sector_upsert`, `service_upsert`, `service_remove`, `config_update` |
| DM → Host | `request_submit`, `request_cancel`, `invocation_result`, `projection_subscribe`, `projection_unsubscribe` |
| Host → DM | `ready`, `request_accepted`, `request_rejected`, `service_invocation`, `request_completed`, `projection_delta`, `pressure`, `diagnostics` |

Major mismatch запрещает live-режим. Minor-расширения согласуются через capabilities; неизвестные изменяющие записи отвергаются, а не пропускаются молча. Неизвестные необязательные поля допустимы только согласно схеме. Ошибка кадра содержит безопасный код и последовательность, без полного секретного payload.

Значения JSON имеют явные типы. Различать массив, объект, `null`, пустой массив и пустой объект; не полагаться на неоднозначное DM associative list кодирование. В частности, сохранить вложенные списки payload машин без изменения формы. Ограничить глубину, длины строк, число записей и размер payload.

Конечные численные значения обязательны; `NaN`/Infinity не отправляются. Недостижимость передаётся статусом. Формат единиц задержек и стоимости зафиксировать отдельно; первоначально воспроизводить существующие формулы, не округляя их произвольно.

## 9. Контракт моста

Предполагаемые операции, не готовые ABI-сигнатуры:

- `open(config)` — начать локальное соединение без ожидания готовности ядра.
- `try_enqueue(frame)` — принять копию ограниченного кадра либо вернуть `would_block`/ошибку; никаких ожиданий свободного места.
- `poll(max_frames, max_bytes)` — забрать ограниченный объём уже полученных данных.
- `status()` — состояние соединения и размеры очередей.
- `close()` — завершить с ограниченным временем освобождения ресурсов.

Socket I/O выполняется вне основного потока BYOND. Перед возвратом нативного вызова данные DM скопированы; фоновые потоки не удерживают borrowed-память аргументов. Ошибки не пересекают ABI исключениями. Время сериализации на стороне DM также ограничивается размером пакета.

`try_enqueue = accepted` не означает, что запрос доставлен или исполнен. Мост не содержит маршрутизации и игровой логики. Обновление его бинарника и запуск Host проходят штатную процедуру развёртывания сервера.

## 10. Топология и маршруты

C# получает исходные факты и сам выполняет дорогие привязки и построение связей. BYOND не должен предварительно вычислять полный граф ради его экспорта.

Опубликовать `GraphSnapshot` целиком: версия, исходная граница, узлы и рёбра, стоимости и необходимые зависимости. Снимок неизменяем для читателей. Старые снимки освобождаются после завершения использующих их расчётов; число одновременно удерживаемых версий ограничено.

Кэши ограничены по количеству и памяти. Ключ учитывает направление, поколения endpoints, режим/политику маршрута и релевантные ревизии. Сначала допустима консервативная инвалидизация по графу; затем локальная по зависимостям, если измерения оправдают сложность.

Маршрут хранит использованные узлы/связи и версию. Изменение сети повторно проверяется на переходах и перед delivery. Правило reroute берётся из действующего NETRUN: не добавлять прозрачный reroute, если его не было. До подтверждения семантики безопасный вариант — завершение затронутого пакета ошибкой маршрута, но это не разрешение менять live-поведение без parity-проверки.

Не копировать полные пути в DM для каждого машинного запроса. Для UI и диагностики использовать отдельный запрос проекции. Публичный DM API, который сейчас синхронно строит маршрут, потребует адаптации на cached/pending либо асинхронный ответ. Все такие потребители перечислить до переключения; скрытый возврат к DM-поиску пути недопустим.

## 11. Запросы и исполнение машин

Основной lifecycle:

```text
Submitted → Accepted → Routing → InTransit → AwaitingInvocation
          → InvocationFinished → ResponseInTransit → Completed
```

Отдельные завершения: `Rejected`, `Failed`, `Cancelled`, `TimedOut`, `OutcomeUnknown`. Каждое завершение имеет код причины; локальный timeout ожидания не доказывает отсутствие побочного эффекта.

1. DM создаёт request ID и отправляет source/destination, контракт операции, payload и deadline.
2. Ядро проверяет объявления сервисов и сетевые условия, моделирует доставку.
3. Ядро выдаёт `service_invocation` со стабильным invocation ID, ссылкой на request, поколениями endpoints, сроком и необходимым контекстом авторизации.
4. DM проверяет epochs, ID/поколение, существование, текущее состояние машины и штатные права операции. Только разрешённый типизированный service handler может исполняться.
5. DM фиксирует результат invocation и возвращает его ядру. Ошибка обработчика превращается в явный ответ, без аварии всего обмена.
6. Ядро моделирует ответный путь согласно правилам протокола и завершает запрос.

Физические права и права пользователя повторно проверяются в DM. C# проверяет сетевую политику. Перенос всей модели прав в C# не входит в первый этап. Контекст пользователя передаётся непрозрачным ограниченным ID, разрешаемым DM; ядро не создаёт привилегии произвольно.

Порядок операций одной машины сохраняется там, где он гарантирован текущим протоколом. Транспортная доставка сама по себе не гарантирует порядок завершения разных сервисов. Для каждого контракта указать concurrency/order policy.

### Повторы и побочные эффекты

- Повтор request ID с тем же содержимым возвращает прежний статус; с другим содержимым отвергается.
- DM ведёт bounded-журнал invocation ID: `executing`, результат, безопасный исход ошибки. Повторное обращение не исполняет действие снова.
- Окно хранения журнала должно покрывать окно replay и время жизни invocation. После забывания результата старый ID отвергается, а не исполняется как новый. Обеспечить это watermark/закрытием поколения; одного TTL недостаточно.
- При рестарте мира старые epochs отвергаются. При рестарте Host во время работы мира DM сохраняет журнал до явного закрытия соответствующего поколения.
- Для произвольных побочных эффектов нет обещания exactly-once при падении между действием и записью результата. Такой исход — `OutcomeUnknown`; автоматического повтора нет. Для безопасных read/idempotent операций повтор разрешает контракт.
- Отмена до выдачи invocation прекращает доставку. После начала действия отмена не откатывает мир и может вернуть `too_late`/неопределённый исход.

Прикладной retry создаёт новый request ID и учитывает семантику операции; replay кадра сохраняет прежние ID. Это разные механизмы.

## 12. Время и планирование

Все игровые дедлайны привязаны к монотонной временной шкале, которую экспортирует DM. Единица начальной схемы — децисекунда; длительности меньшей точности и текущие формулы отдельно проверить. Часы ядра не идут вперёд без подтверждённого DM-времени. Пауза мира не ускоряет сетевые пакеты.

DM-адаптер обрабатывает переполнение/сброс исходных часов и экспортирует монотонное значение; допустимый численный диапазон фиксируется в схеме. После нового world epoch время начинается заново. Назад время в пределах epoch не принимается.

Внутри одного времени порядок задают входная последовательность, позиция записи и стабильный serial таймера. Случайность, если требуется существующими правилами, использует явный seed и воспроизводимый источник.

При отставании нельзя исполнять неограниченный catch-up одним циклом. Транспорт соблюдает deadlines, bounded work и приоритеты. Дедлайн включает ожидание во входной очереди и загрузку ядра. Heartbeat/разрыв соединения измеряются физическим временем отдельно.

## 13. Перегрузка и бюджет BYOND

Ограничить все очереди, число запросов, размер журналов replay/dedup, кэши, число подписок, snapshot staging и объём удерживаемых графов. Лимиты задаются конфигурацией и видны в диагностике.

Приоритеты: служебные ACK/синхронизация и ограничения доступности; уже принятые завершения; интерактивные запросы; фоновые состояния и проекции. Для низких приоритетов нужна защита от бесконечного голодания. Данные одного последовательного потока не переупорядочиваются приоритетом задним числом.

Заменяемые состояния и проекции можно объединять до присвоения sequence. Команды и результаты побочных эффектов нельзя молча удалять. При нехватке места новый запрос получает явный `busy`; принятый запрос сохраняет гарантированный способ завершения. Зарезервировать ёмкость для результатов и ACK.

DM-pass имеет лимит байтов, записей и времени применения; остаток переносится. Объём, уже извлечённый из моста, но ещё не применённый, тоже ограничен. Если очередь фактов переполнена и целостность не гарантирована, live останавливается до resync.

Реакция на lag: показывать pending/degraded, ограничивать admission. Не блокировать игровой тик и не делать автоматический полный DM-пересчёт на каждый timeout.

## 14. Проекции и совместимость

DM хранит только необходимые опубликованные данные и результаты. Карта и консоль подписываются на область интереса; закрытие UI снимает подписку/lease. Общие изменения готовятся один раз, а не отдельно для каждой консоли.

Проекции имеют собственную revision, базовую версию и full-resync при разрыве цепочки. Представление может отставать; оно не является разрешением выполнить операцию. Не публиковать большие деревья маршрутов или каждый виртуальный hop без подписки.

Сохранить внешний вид и игровые действия существующего интерфейса. Допустимые новые состояния: ожидается расчёт, очередь перегружена, NETRUN недоступен. Их текст и поведение согласовать с текущим UX при реализации.

## 15. Сбой, перезапуск и переключение

Режимы конфигурации: `dm`, `shadow`, `external`. В `shadow` C# получает копии входов, но не имеет права выдавать реальные эффекты. Сопоставление результатов не удваивает вызовы машин.

Потеря Host переводит external в `Unavailable`: новые запросы отклоняются, неизвестные эффекты не повторяются. Допустимый автоматический рестарт Host выполняется с backoff; затем handshake, новый engine/binding epoch, снимок и catch-up.

Для первой live-версии восстановление полного транспорта не обязательно: принятые, но не выданные обращения завершаются ошибкой; выданные сверяются с DM-журналом, а не повторяются. Если результат потерян и не восстанавливается, статус `OutcomeUnknown`. Статическая сеть восстанавливается из мира. Это должно быть явно видно вызывающей машине.

Плановое переключение: закрыть admission → drain с ограниченным сроком → классифицировать незавершённые запросы → сменить binding epoch → собрать состояние выбранного движка → открыть admission. Кадры прежнего владельца отбрасываются.

Не обещать бесшовный fallback между двумя транспортами. Самый простой безопасный откат на первых этапах — выбор `dm` со следующего запуска раунда. Переключение посреди раунда разрешать только после реализации и проверки описанного барьера.

## 16. Безопасность и эксплуатация

Host слушает только локальный endpoint. Соединение привязывается к экземпляру мира; handshake использует секрет сеанса или эквивалентную защиту локального endpoint. Секрет не включается в репозиторий и логи. Игровой клиент не может обращаться к IPC напрямую.

Проверять размер и схему до обработки; операции обслуживаются allowlist сервисов. Не исполнять переданные DM-proc names, shell commands, пути файлов или произвольный C#-код. Логи payload по умолчанию отключены; чувствительные данные прав и пользователей редактируются.

Развёртывание включает версию Host и моста, конфигурацию endpoint, выбор режима, supervisor/штатный механизм запуска и процедуру остановки. Не менять инфраструктуру сервера в рамках разработки без отдельного согласования.

## 17. Метрики и диагностика

Измерять отдельно:

- DM: сбор фактов, сериализация, native calls, десериализация, применение результатов — total/p95/p99/max и число записей.
- Host: topology build, route compute, cache hit/miss, транспорт, GC/allocations, CPU и память.
- Обмен: байты, задержка ACK, backlog, возраст старейшего факта, `world input → graph publish` lag.
- Запросы: admission, queue wait, route wait, виртуальная доставка, DM execution, ответ; p50/p95/p99 и причины отказов.
- Надёжность: пропуски, replay, resync, dedup hits, unknown outcomes, рестарты и отказы схемы.
- Игровая нагрузка: число узлов/связей, активных запросов, консолей и интенсивность churn.

End-to-end задержку в физических часах измеряет DM по request ID, без сравнения несинхронизированных часов процессов. Логическую задержку показывать отдельно.

Диагностический экспорт должен позволять воспроизведение очищенной последовательности входов в автономном C# runner. Сырые пользовательские payload не сохраняются автоматически.

## 18. Проверки и критерии приёмки

### Корректность

- Сопоставление графа: узлы, рёбра, доступность, стоимости, привязки и Z-геометрия.
- Маршруты: достижимость и стоимость; равные альтернативы допустимы только если правила не требуют конкретного пути.
- Воспроизведение запросов и ответов, отказов и отмен относительно DM-эталона.
- Сохранение формы вложенных payload, null и пустых коллекций.
- Удаление/пересоздание, замена компонента, движение и отключение во время snapshot, route build, transit и перед invocation.
- Частичные/дублированные/повреждённые кадры, gap/replay, переполнение очередей, несовместимая версия.
- Падение Host до/после выдачи invocation и после DM-эффекта до ACK.
- Отсутствие повторных эффектов в поддерживаемом окне dedup; явный unknown за пределами доказуемого результата.
- Отмена и timeout до/после начала исполнения, обратный путь при изменившейся сети.
- Длительная работа с bounded памятью и стабильным восстановлением.

### Производительность

Наборы: спокойная станция; одновременный опрос машин; массовые изменения питания; регистрация/удаление/движение инфраструктуры; активный UI; холодные кэши; искусственно медленный/недоступный Host.

Одинаковые входы сравниваются с текущим DM и external. Учитываются оба процесса, p99 времени основного потока, суммарная CPU/память и задержка обслуживания машин. Ускорение C# без разгрузки DM не является успехом.

До завершения этапа 0 численные цели не утверждены. Обязательная форма release gate: измеримое снижение p95/p99 DM-стоимости целевых операций, отсутствие превышения согласованного бюджета применения, приемлемая end-to-end задержка и отсутствие необъяснённых parity-расхождений. На этапе 0 записать конкретные пороги и нагрузочные параметры в отдельный baseline-отчёт; без них live-переключение не считается принятым.

Использовать существующие `code/modules/unit_tests/netrun_*.dm`, особенно topology, routes, routing cache, transport, packets, delivery queue, machine services, scheduler и execution. Конкретные имена и команды runner проверить по актуальному checkout. Добавлять тесты контрактов и отказов, не переписывать существующие проверки механически.

Если частичное переключение чрезмерно усложняет текущий транспорт, этапы 5–7 можно объединить в один live-cutover после полного shadow, сохранив раздельную разработку и проверки.

## 20. Основные риски и решения

| Риск | Решение |
|---|---|
| DM строит граф перед экспортом | Передавать исходные факты; вычисление связей выполняет C# |
| Сериализация съедает выигрыш | Deltas, batching, ограничения, измерения до смены формата |
| Скрытый синхронный поиск из UI/проверки | Аудит call sites, cached/pending API, счётчики legacy-пути |
| Различие игровых правил | Эталонные сценарии и shadow; изменения правил отдельной задачей |
| Устаревший граф после отключения | Availability overlay и ожидание затронутых расчётов |
| Двойное исполнение | Один live-владелец, binding epoch, invocation journal |
| Неопределённый эффект после сбоя | OutcomeUnknown, запрет небезопасного retry |
| Полный снимок тормозит тик | Chunking, журнал изменений, ограниченный staging |
| Неограниченные очереди/история | Admission control, quotas, watermarks и диагностика |
| Слишком много задач за один проход | Лимиты на обеих сторонах, bounded catch-up и применение |
