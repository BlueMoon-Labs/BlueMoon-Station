# Проверка сейвов

## Просмотр на сервере

Команда **Debug → Info → Inspect Player Saves** доступна с правом `R_DEBUG`.
Введите ckey, выберите файл и действие: просмотр или скачивание исходника.
Игрок может быть офлайн. Для выбора другого файла снова откройте команду.
Каждое обращение к файлу записывается в админский лог.

Список включает JSON, `.recovery`, старые `.sav` и `.updatebac`, отдельные
разделы в `.d/` и сейвы vore. Просмотр JSON форматирует текст; повреждённый JSON
показывается как есть. Старый SAV читается на временной копии и показывается
в текстовом формате BYOND. Исходник скачивается без преобразования.
Предпросмотр ограничен 1 МиБ; больший файл нужно скачать.

Это сохранённое состояние на диске: изменения, которые игрок ещё не сохранил,
в него не входят. Для разбора полного JSON-сейва скачайте корень, `.recovery`
и нужные файлы каталога `.d/`; имя раздела в `directories` корня соответствует
файлу `<md5 имени раздела>.sav.json`. В имени скачанного файла ckey добавляется
как префикс, а разделители каталогов заменяются на `--`.
Отдельные скачивания не образуют атомарный снимок аккаунта онлайн-игрока.

## Проверка копий

`audit.py` проверяет перенос `.sav` и `.updatebac` в JSON на копиях файлов.
Утилита собирает тестовый мир с типами проекта, без запуска станции, и сравнивает
данные до и после преобразования.

Нужны Python 3.11+, BYOND и Node.js. Для распаковки архива используется `tar`.
Команды запускаются из корня репозитория:

```powershell
python tools/player_saves/audit.py --archive D:/saves/player_saves.7z --work-dir D:/saves/audit
```

Параметры:

- `--source-dir` — каталог с распакованными сейвами вместо `--archive`.
- `--storage-roundtrip` — также проверить запись JSON на диск и повторную загрузку.
- `--limit N` — проверить первые N файлов.
- `--byond-bin` — каталог с компилятором и DreamDaemon, если нужен конкретный BYOND.
- `--benchmark` — замерить чтение и запись на рабочих копиях.

Результаты сохраняются в `report.json`, пути исходных файлов — в `manifest.json`.
Ненулевой код выхода означает ошибку, расхождение данных, отсутствие версии
или автоматическое исправление сейва BYOND. Такие файлы нужно разобрать отдельно.
Данные удалённых из проекта типов могут быть недоступны текущему BYOND.
Рабочий каталог содержит данные игроков; не добавляйте его в Git.

## Синтетический замер в dm-test

```powershell
node tools/build/build.js dm-test --unit-test-profile=hermetic --define=PLAYER_SAVE_TESTS --define=PLAYER_SAVE_BENCHMARK
```

Фикстура содержит 1280 узлов: 75 настроек корня и пять слотов по 240 полей.
Строка `PLAYER_SAVE_BENCHMARK` в логе содержит среднее время в миллисекундах
по 20 повторам. Загрузка слота сравнивает открытие и чтение его полей;
сохранение меняет 239 полей и выполняет commit/Flush. Отдельно измеряются
неизменённый commit, настройка корня, имена слотов и `save_character` с обычными
префами. Холодный замер создаёт новый датум хранилища; дисковый кэш ОС не очищается.
Порогов времени в тесте нет: сравнивайте одинаковые команды на одной машине.
Без `PLAYER_SAVE_BENCHMARK` замер не включается в сборку.

Поля `document_setting`, `document_unchanged` и `document_character_patch`
измеряют операции через документ на той же фикстуре. Поля `json_single_pref_e2e`,
`json_save_preferences_e2e` и `json_save_character_e2e` включают настоящие
писатели preferences и модульные расширения.
Для сохранения персонажа и настроек целиком замер чередует новый и совместимый
пути попарно, меняя порядок на каждом повторе. Поля с `compat_e2e` показывают
совместимый путь в том же процессе и на той же фикстуре.
`json_load_cold_with_root_copy` — контроль холодной загрузки с прежней лишней
копией корня; он чередуется с `json_load_cold` в том же порядке.

`json_preferences_unchanged_e2e` и `json_character_unchanged_e2e` измеряют повторное
полное сохранение без правок. `json_names_after_save` измеряет только получение имён
после успешного сохранения нового имени, с проверкой его актуальности.

Синтетические storage-операции и e2e используют разные фикстуры: для e2e создаётся
обычный `datum/preferences`. `compat_e2e` тоже пишет JSON, но через совместимый
savefile-путь; это не замер старого дискового SAV. В `binary_load` исходный savefile
остаётся открытым. Эти числа сами по себе не доказывают паритет старого и нового
форматов при одинаковом состоянии кэшей.

## Документы и совместимость

`snapshot()` возвращает документ проверенного поколения. `read(key)` выдаёт
отдельное значение, а `write(key, value)` отделяет изменяемые узлы от исходного
снимка. Списки вызывающего не становятся частью сохранённого кэша по ссылке.
Повторный `commit()` без изменений не сериализует дерево. Устаревшая ревизия
отклоняется до записи: нужно прочитать актуальный снимок и повторить изменения.
Совместимый commit через savefile тоже проверяет ревизию с момента открытия;
для аккаунта проверка выполняется до записи разделов персонажа.

Одиночные настройки и чтение metadollars используют документ напрямую.
Базовые писатели настроек и персонажа записывают поля прямо в документ через
`WRITE_PLAYER_SAVE`. Модульные дополнения пока заполняют совместимый savefile;
при сохранении эти поля объединяются с документом. Равные значения не копируют
узлы и не помечают документ изменённым. Неизвестные поля и вложенные узлы остаются
на месте. Перенос старого монолитного сейва, импорт и экспорт сохраняют прежний
путь через savefile. Буфер одиночных настроек применяется до основных полей,
поэтому устаревшее значение из буфера не перекрывает актуальную переменную.

Корень по-прежнему публикуется после раздела персонажа. Меню читает имена из
проверенных документов, без сборки анкет в savefile. Отдельного индекса имён
нет: повреждение раздела по-прежнему обнаруживается при холодном открытии меню
и вызывает согласованное восстановление предыдущего снимка.
После сохранения меню использует проверенный документ из кэша, если его поколение
и ревизия актуальны. Удаление слота публикует правку корневого каталога, не
пересохраняя остальные анкеты; файлы удалённой ветви остаются для восстановления
предыдущего поколения. Старый монолит при удалении сначала переносится целиком.

Кэш живёт в датуме хранилища и проверяет ревизии записей других датумов.
В памяти остаются корень и не более двух последних разделов; остальные
документы освобождаются после завершения использующей их операции.
Редактирование файлов внешними инструментами требует остановки сервера.
Формат v1 и алгоритм контрольной суммы не изменены.

## Миграция и резервные копии

Сервер создаёт JSON автоматически при первом сохранении аккаунта. Старые `.sav`
и `.updatebac` остаются на месте, но после перехода больше не обновляются.
В резервную копию должны входить все три части хранилища:

- `preferences.sav.json`;
- `preferences.sav.json.recovery`;
- каталог `preferences.sav.json.d/` целиком.

Два поколения позволяют восстановиться после неполной записи. Если оба повреждены
или версия неизвестна, запись блокируется. Редактировать файлы вручную следует
при остановленном сервере.

## Возврат к формату SAV

Перед откатом сервера выгрузите актуальные JSON в `.sav`, работая с копией данных:

```powershell
python tools/player_saves/audit.py --source-dir D:/saves/copy --export-legacy --work-dir D:/saves/export
```

Результат появится в `D:/saves/export/legacy/`. Утилита проверит файлы повторным
чтением. Перед установкой проверьте их на старой сборке. Простое удаление JSON
вернёт устаревшее состояние из исходных `.sav`.

## Файлы для обмена персонажами

Игровые кнопки экспорта и импорта используют отдельный формат `bluemoon-character`.
Он содержит только разрешённые поля персонажа. Валюта, права и другие данные
аккаунта через него не передаются. Список полей и проверки находятся в
[player_save_transfer.dm](../../code/modules/client/player_save_transfer.dm).
Дисковые JSON-сейвы через игровой импорт не загружаются.
