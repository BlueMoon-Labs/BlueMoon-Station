SubSystem flags (Please design any new flags so that the default is off, to make adding flags to subsystems easier)

MC_RUNNINGReturns true if the MC is initialized and running. Optional argument init_stage controls what stage the mc must have initializted to count as initialized. Defaults to INITSTAGE_MAX if not specified.
SS_NO_INITsubsystem does not initialize.
SS_NO_FIREsubsystem does not fire. (like can_fire = 0, but keeps it from getting added to the processing subsystems list) (Requires a MC restart to change)
SS_BACKGROUNDSubsystem only runs on spare cpu (after all non-background subsystems have ran that tick) SS_BACKGROUND has its own priority bracket, this overrides SS_TICKER's priority bump
SS_NO_TICK_CHECKsubsystem does not tick check, and should not run unless there is enough time (or its running behind (unless background))
SS_TICKERTreat wait as a tick count, not DS, run every wait ticks. (also forces it to run first in the tick (unless SS_BACKGROUND)) (implies all runlevels because of how it works) This is designed for basically anything that works as a mini-mc (like SStimer)
SS_KEEP_TIMINGkeep the subsystem's timing on point by firing early if it fired late last fire because of lag ie: if a 20ds subsystem fires say 5 ds late due to lag or what not, its next fire would be in 15ds, not 20ds.
SS_POST_FIRE_TIMINGCalculate its next fire after its fired. (IE: if a 5ds wait SS takes 2ds to run, its next fire should be 5ds away, not 3ds like it normally would be) This flag overrides SS_KEEP_TIMING

#define
MC_RUNNING
(INIT_STAGE ...)

Returns true if the MC is initialized and running. Optional argument init_stage controls what stage the mc must have initializted to count as initialized. Defaults to INITSTAGE_MAX if not specified.

#define
MC_STATE_CLEAN_MARK

С этой строки начинается сводка, затёртая штатным завершением.

#define
MC_STATE_FAILURE_LIMIT

После скольких неудачных записей подряд чёрный ящик выключается до конца раунда.

Запись идёт по нескольку раз в секунду, и падающая на каждой запись - это лог, забитый одинаковой строкой, то есть худший из возможных исходов для диагностики краша.

#define
MC_STATE_INTERVAL_LOG_FACTOR

Во сколько раз должен измениться интервал, чтобы об этом написали в лог. Без порога строка идёт на каждый шаг подстройки.

#define
MC_STATE_MAX_INTERVAL

Реже этого не пишется даже на самой медленной файловой системе: четыре секунды слепоты - предел.

#define
MC_STATE_MIN_INTERVAL

Чаще этого сводка не пишется никогда - один раз за проход петли МК.

#define
MC_STATE_QUEUE_PREVIEW

#define
MC_STATE_SNAPSHOT_FILE

Куда пишется сводка: data/ переживает раунд и перезапуск процесса, там же лежит GracefulEnding.json.

#define
MC_STATE_TASK_MAX_LEN

Сколько символов задачи подсистемы попадает в сводку.

#define
MC_STATE_TICK_BUDGET

Какую долю тика (в процентах) чёрному ящику разрешено занимать в среднем.

Цена одной записи зависит от платформы на два порядка: rustg_file_write открывает, пишет и закрывает файл на каждый вызов, и там, где Linux с page cache тратит десятки микросекунд, Windows с антивирусом на пути тратит миллисекунды (замер юнит-теста mc_state_snapshot_interval_adapts на рабочей машине: 8.2 мс, то есть 40% тика). Поэтому в дефайне не частота, а бюджет: частоту подсистема подбирает сама под замер.

#define
MC_STATE_TICK_SKIP_ABOVE

Выше какой занятости тика (в процентах) запись сводки откладывается до следующего прохода.

Бюджет выше держит СРЕДНЮЮ цену, но выброс одной записи он не трогает: сколько стоит вызов rustg_file_write, столько он и стоит. В проде 23.08 отдельные записи стоили 121% тика (раунд 10087) и 80% (10091), и оба раза - в шторме логинов, то есть прибор добивал тик ровно тогда, когда миру и без него было тяжело. Планка выбрана так, чтобы обычный тик (единицы-десятки процентов) записи не терял вовсе, а тик на исходе бюджета - терял.
